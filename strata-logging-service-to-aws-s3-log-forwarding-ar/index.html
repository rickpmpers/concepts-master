# Architecture & Configuration Guide: Forwarding Strata Logging Service Logs to AWS S3

# 1. Executive Summary & Solution Pattern

## 1.1 Overview

Organizations deploying Palo Alto Networks Next-Generation Firewalls (NGFW) and Prisma Access leverage Strata Logging Service (formerly Cortex Data Lake) as a cloud-native repository for centralized network security telemetry. While Strata Logging Service provides high-performance querying and analytics within the Palo Alto Networks ecosystem, enterprise security and governance requirements often mandate forwarding log streams to customer-owned object storage.

Exporting logs to Amazon Simple Storage Service (Amazon S3) fulfills critical enterprise objectives:

  - **Long-Term Retention & Regulatory Compliance**: Adhering to standards such as PCI-DSS, HIPAA, SOC 2, and NIST 800-53 by storing audit trails in immutable, cost-effective cloud storage.
  - **Centralized Security Data Lake**: Feeding downstream Security Information and Event Management (SIEM) systems (e.g., Splunk, Microsoft Sentinel), Security Data Lakes (e.g., Snowflake, Amazon Security Lake), and analytics platforms.
  - **Serverless Analytics**: Enabling ad-hoc threat hunting and compliance reporting using Amazon Athena, AWS Glue, and Amazon QuickSight directly on top of raw S3 log files.

## 1.2 Architectural Data Flow

The solution pattern uses an event-driven, push-based log forwarding mechanism managed natively by Strata Logging Service:

```
+--------------------------+
|  Palo Alto Networks      |
|  NGFW / Prisma Access    |
+------------+-------------+
             |
             v (Secure Telemetry / SSL)
+-------------------------------------------------------------+
|  Strata Logging Service (Cortex Data Lake)                  |
|  - Real-time ingestion & indexing                          |
|  - Batching Engine (1,000 records or 10-second threshold)  |
|  - Snappy Compression & JSON formatting                     |
|  - Log Forwarding Profile Engine                           |
+----------------------------+--------------------------------+
                             |
                             | Cross-Account IAM Role Assumption
                             | (sts:AssumeRole + External ID)
                             | HTTPS PUT (Encrypted in transit)
                             v
+-------------------------------------------------------------+
|  Customer AWS Account                                       |
|  +-------------------------------------------------------+  |
|  |  Amazon S3 Bucket (Destination)                       |  |
|  |  - Folder Hierarchy:                                  |  |
|  |    /<prefix>/<logsource>.<logtype>/YYYY/MM/DD/*.json  |  |
|  |  - Server-Side Encryption (SSE-S3 / SSE-KMS)          |  |
|  |  - S3 Lifecycle Policies (Transition to IA / Glacier) |  |
|  +---------------------------+---------------------------+  |
|                              |                              |
|                              v                              |
|  +-------------------------------------------------------+  |
|  |  Downstream Processing & Analytics                    |  |
|  |  - Amazon Athena (Serverless SQL Queries)             |  |
|  |  - AWS Glue Data Catalog                              |  |
|  |  - SIEM / Third-Party Data Pipeline Ingestion         |  |
|  +-------------------------------------------------------+  |
+-------------------------------------------------------------+
```

## 1.3 Core Technical Characteristics

  - **Batching Behavior**: Strata Logging Service aggregates logs into batches based on either a size limit of **1,000 log lines** or a time limit of **10 seconds**, whichever is reached first.
  - **Payload Format & Compression**: Logs are formatted as newline-delimited JSON objects and compressed using **Snappy** compression (.snappy) to optimize network throughput and S3 storage footprints.
  - **S3 Partitioning Structure**: Log files are delivered using a date-partitioned folder structure:
    `s3://<bucket-name>/<optional-folder-prefix>/<logsource>.<logtype>/<year>/<month>/<day>/<batch-id>.json.snappy`
  - **Buffering & Outage Resilience**: In the event of network interruption or AWS authentication failure, Strata Logging Service buffers undelivered logs for up to **72 hours**. Status notification alerts are dispatched via email every 60 minutes. Once connectivity is restored, administrators can initiate a manual **Log Replay** spanning up to 3 days to recover buffered logs without data loss.

# 2. Security Architecture & IAM Authentication

## 2.1 Cross-Account IAM Role Assumption (Recommended Best Practice)

To follow security best practices and avoid managing static, long-lived AWS access keys, Strata Logging Service supports cross-account authentication using AWS Identity and Access Management (IAM) role assumption (sts:AssumeRole) with an **External ID**.

1.  Strata Logging Service operates within a dedicated Palo Alto Networks AWS account.
2.  The customer creates an IAM Role in their target AWS account granting write (s3:PutObject) permissions to the specific S3 bucket.
3.  The IAM Role establishes a trust relationship allowing the Palo Alto Networks account to assume the role, strictly conditioned on matching a unique, customer-defined External ID (preventing the Confused Deputy problem).

## 2.2 Alternative: IAM User with Access Keys

Strata Logging Service also supports standard AWS Access Key ID and Secret Access Key pairs. While functional, this method requires ongoing credential lifecycle management, secret rotation, and introduces credential leakage risks. Cross-Account IAM Role assumption is strongly advised.

# 3. Step-by-Step Configuration Guide

## Phase 1: Configure AWS Infrastructure

### Step 1.1: Create and Configure the Amazon S3 Bucket

1.  Open the AWS Management Console and navigate to **Amazon S3** > **Create bucket**.
2.  **Bucket Name**: Provide a globally unique, DNS-compliant name (e.g., `company-strata-logs-<aws-region>`).
3.  **AWS Region**: Select the target AWS Region. For optimal performance and reduced egress costs, choose the region closest to your Strata Logging Service instance.
4.  **Object Ownership**: Select **Bucket owner enforced** (disables ACLs and standardizes object ownership).
5.  **Block Public Access**: Ensure **Block all public access** remains enabled.
6.  **Bucket Versioning**: Optional, but recommended for compliance auditability.
7.  **Default Encryption**:
      - Enable **Server-side encryption with Amazon S3 managed keys (SSE-S3)** (AES-256) by default.
      - If using **AWS Key Management Service (SSE-KMS)**, ensure the KMS key policy explicitly permits `kms:GenerateDataKey` and `kms:Decrypt` actions for the Palo Alto Networks assuming role.
8.  Click **Create bucket**.

### Step 1.2: Create the IAM Permissions Policy

1.  Navigate to **IAM** > **Policies** > **Create policy**.
2.  Select the **JSON** tab and input the following least-privilege policy (replace `company-strata-logs-bucket` with your actual bucket name):

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowStrataLoggingServiceS3PutObject",
      "Effect": "Allow",
      "Action": [
        "s3:PutObject"
      ],
      "Resource": [
        "arn:aws:s3:::company-strata-logs-bucket",
        "arn:aws:s3:::company-strata-logs-bucket/*"
      ]
    }
  ]
}
```

3.  Click **Next**, name the policy `PaloAltoStrataLoggingS3Policy`, and click **Create policy**.

### Step 1.3: Create the Cross-Account IAM Role

1.  In the IAM console, navigate to **Roles** > **Create role**.
2.  **Trusted Entity Type**: Select **AWS account** > **Another AWS account**.
3.  **Account ID**: Enter the Palo Alto Networks AWS Account ID retrieved from the Strata Logging Service / Strata Cloud Manager UI (displayed during log forwarding profile creation).
4.  **An External ID**: Check **Require external ID**. Enter a strong, unique external identifier (passcode/secret string). Record this value for configuration in Strata Logging Service.
5.  Click **Next**.
6.  **Add Permissions**: Attach the `PaloAltoStrataLoggingS3Policy` created in Step 1.2.
7.  Click **Next**, name the role (e.g., `StrataLoggingServiceForwardingRole`), and verify the Trust Policy JSON:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowStrataLoggingServiceAssumeRole",
      "Effect": "Allow",
      "Principal": {
        "AWS": "arn:aws:iam::<PALO_ALTO_NETWORKS_ACCOUNT_ID>:root"
      },
      "Action": "sts:AssumeRole",
      "Condition": {
        "StringEquals": {
          "sts:ExternalId": "<YOUR_CONFIGURED_EXTERNAL_ID>"
        }
      }
    }
  ]
}
```

8.  Click **Create role**.
9.  Select the newly created role and copy its **Role ARN** (format: `arn:aws:iam::<YOUR_ACCOUNT_ID>:role/StrataLoggingServiceForwardingRole`).

## Phase 2: Configure Strata Logging Service / Strata Cloud Manager

### Step 2.1: Access the Log Forwarding Configuration

1.  Log in to the Palo Alto Networks Hub or **Strata Cloud Manager**.
2.  If using Strata Cloud Manager:
    - Navigate to **Workspaces** / **System Settings** > **Strata Logging Service** > **Log Forwarding**.
3.  If using the dedicated Strata Logging Service app:
    - Select your target **Strata Logging Service instance**.
    - Navigate to **Log Forwarding** > **Cloud Storage**.
4.  Click **Add Amazon S3 Profile** (or **+ Add Profile**).

### Step 2.2: Define S3 Profile Parameters

1.  **Profile Name**: Enter a descriptive name (e.g., `AWS-S3-Security-DataLake`).
2.  **S3 Bucket Name**: Enter the exact bucket name configured in AWS (e.g., `company-strata-logs-bucket`).
3.  **Region**: Select the AWS geographic region corresponding to your bucket (e.g., `us-west-2`, `us-east-1`).
4.  **Authentication Method**: Select **IAM Role**.
    - **IAM Role ARN**: Paste the ARN copied from Step 1.3 (`arn:aws:iam::<ACCOUNT_ID>:role/StrataLoggingServiceForwardingRole`).
    - **External ID**: Enter the exact External ID string defined in the IAM Role trust policy.
    - *(Note: If using Access Keys, select Access Key and provide Access Key ID and Secret Access Key).*

### Step 2.3: Test Connection

1.  Click **Test Connection**.
2.  Strata Logging Service will attempt to assume the role and transmit an empty test event file to a temporary prefix path (`sls_test_events/`) inside your S3 bucket.
3.  Verify that the connection test returns **Success**. (If the test fails, check IAM trust policy, external ID, and S3 put object permissions).
4.  Click **Next**.

### Step 2.4: Specify Payload & Log Types

1.  **Payload Format**: Confirm format is set to **JSON**.
2.  **Status Notifications**: Provide an administrative email address to receive real-time alerting if Strata Logging Service encounters S3 delivery failures.
3.  **Log Selection & Filtering**:
    - Click **Add Log Type** to choose the log datasets to forward:
      - **Firewall Traffic** (network sessions)
      - **Threat** (antivirus, anti-spyware, vulnerability, WildFire detections)
      - **URL Filtering** (web browsing activity)
      - **DNS Security** (DNS resolution queries and malicious domain detections)
      - **GlobalProtect** (VPN and remote access connection events)
      - **Decryption** (SSL/TLS decryption logs)
      - **System & Configuration** (administrative audit trails and operational alerts)
      - **Authentication & User-ID** (identity mappings)
    - **Filter Queries (Optional)**: To forward only high-priority telemetry (e.g., only high/critical threats or specific zone traffic), enter a filter query using the Strata Logging Service Query Builder syntax. Leave empty to forward all logs for the selected type.
4.  Click **Save** to apply the configuration.

### Step 2.5: Verify Forwarding Status

1.  Return to the **Log Forwarding** dashboard.
2.  Confirm the profile status displays a green checkmark with status **Running**.
3.  Allow 5–15 minutes for telemetry generation, then inspect the AWS S3 bucket console.
4.  Confirm folder hierarchy is created (e.g., `panw_logs/traffic/2026/09/22/...`).

# 4. Downstream Processing & Analytics Pattern

## 4.1 Log Object File Structure & Decompression

Log files written to S3 are compressed with Google Snappy. Downstream processing pipelines (Lambda, Glue, EMR, or custom containers) can decompress records using standard Snappy libraries.

Example Python script for local/serverless decompression and inspection:

```python
import boto3
import snappy
import json

s3 = boto3.client('s3')
bucket = 'company-strata-logs-bucket'
key = 'panw_logs/traffic/2026/09/22/log_batch_001.json.snappy'

response = s3.get_object(Bucket=bucket, Key=key)
compressed_data = response['Body'].read()
uncompressed_data = snappy.uncompress(compressed_data).decode('utf-8')

for line in uncompressed_data.strip().split('\n'):
    log_record = json.loads(line)
    print(f"Time: {log_record.get('receive_time')}, Action: {log_record.get('action')}, App: {log_record.get('app')}")
```

## 4.2 Querying Logs with Amazon Athena

Amazon Athena allows security analysts to perform interactive SQL queries against raw logs in S3 without managing database infrastructure.

Sample Athena DDL for creating an external table over Strata Traffic logs:

```sql
CREATE EXTERNAL TABLE IF NOT EXISTS strata_traffic_logs (
  receive_time string,
  serial_number string,
  type string,
  subtype string,
  source_ip string,
  destination_ip string,
  source_port int,
  destination_port int,
  protocol string,
  action string,
  app string,
  bytes bigint,
  packets bigint,
  rule string
)
ROW FORMAT SERDE 'org.openx.data.jsonserde.JsonSerDe'
WITH SERDEPROPERTIES (
  'ignore.malformed.json' = 'FALSE',
  'dots.in.keys' = 'FALSE',
  'case.insensitive' = 'TRUE'
)
STORED AS INPUTFORMAT 'org.apache.hadoop.mapred.TextInputFormat'
OUTPUTFORMAT 'org.apache.hadoop.hive.ql.io.HiveIgnoreKeyTextOutputFormat'
LOCATION 's3://company-strata-logs-bucket/panw_logs/traffic/'
TBLPROPERTIES ('classification'='json');
```

# 5. Operational Maintenance, Monitoring & Disaster Recovery

## 5.1 Outage Recovery & The 72-Hour Buffer Window

  - **Buffering**: If the AWS destination becomes inaccessible (e.g., expired role permissions, bucket policy changes, or AWS regional disruptions), Strata Logging Service buffers logs for up to **72 hours**.
  - **Alerting**: The configured administrator email receives recurring alerts every 60 minutes.
  - **Log Replay**: Once S3 bucket or IAM connectivity is restored, navigate to **Strata Logging Service** > **Log Forwarding** > select the profile > choose **Log Replay**. Select the timeframe (up to 3 days) to replay buffered or missed logs.
  - **Critical Threshold**: If connectivity issues remain unresolved beyond 72 hours, unforwarded logs exceeding the retention buffer are permanently discarded.

## 5.2 S3 Lifecycle & Cost Optimization Strategy

Network security logs generate significant data volume. Implement an **S3 Lifecycle Configuration** to balance compliance requirements with cost efficiency:

1.  **Day 0 - 30**: Store in **S3 Standard** for rapid incident response and interactive Athena queries.
2.  **Day 31 - 90**: Transition objects to **S3 Standard-Infrequent Access (S3 Standard-IA)** to reduce storage costs by ~40%.
3.  **Day 91 - 365+**: Transition objects to **Amazon S3 Glacier Flexible Retrieval** or **Glacier Deep Archive** for multi-year compliance retention.
4.  **Expiration**: Automatically expire/delete objects after organizational retention period expires (e.g., 365 days or 7 years).
